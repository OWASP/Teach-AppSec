# Introduction to Operations Security

## Part 1: Theory

### What is Operational Security?

Operational Security is the process of protecting an organization's operations, processes, and assets from threats by implementing structured controls and practices.

- It is about the daily execution of security: detecting, responding, monitoring, and adapting.
- It ensures that once risks are identified and policies are created, there is a practical mechanism to enforce them.
- Operational Security has the target of reducing the impact of external threats and internal vulnerabilities as close to zero as possible.

This is achieved by:

- **Monitoring** every activity and analyzing alerts generated from devices through event management systems.
- **Responding** quickly to threats using well-defined incident response playbooks.
- **Configuring** security devices (e.g., perimeter firewalls, data center firewalls, endpoint security, application hardening) according to predefined approved policies and hardened configurations.
- **Tracking** new threats continuously, analyzing their potential impact, and preparing appropriate defenses.
- **Performing** controlled changes at all levels (infrastructure, applications, processes) to keep the environment up to date and aligned with best practices.
- **Building resiliency** by designing redundancy and failover scenarios, ensuring that critical systems can automatically fall back to standby environments when needed.
- **Implementing a robust backup strategy**, including secure and tested data backups, to ensure recovery and reduce downtime in case of failures or attacks.
- **Implementing** approved access control policies to ensure proper management of privileged access, strict governance of software installations, and clear rules for data classification and ongoing data monitoring.

## Key Domains of Operational Security

### 1. Change Management

#### Methods and Impact on Operations

Every change to systems, networks, or applications introduces potential risk. Change management provides structure to ensure security review, approvals, rollback plans, and monitoring. Without this structure, unapproved or poorly designed changes may introduce vulnerabilities, disrupt operations, or bypass compliance requirements.

#### Examples of Changes in Application Security

**Configuration Changes**

- *Examples:* Adjustments to application parameters, authentication rules, or logging settings.
- *How to handle:* Require approval and validation in a test environment; ensure a rollback plan exists.
- *Example:* Reducing password complexity requirements.
- *Impact:* Could weaken authentication security and increase brute-force attack risk.

**Code Changes / Application Updates**

- *Examples:* Modifications to source code, libraries, or APIs.
- *How to handle:* Mandatory code review, static/dynamic security testing (SAST/DAST), peer approval before release.
- *Example:* Updating a web app with a new input validation function.
- *Impact:* If improperly tested, could introduce injection vulnerabilities (e.g., SQLi, XSS).

**Infrastructure & Deployment Changes**

- *Examples:* Deployment pipelines, server upgrades, or changes to the hosting environment.
- *How to handle:* DevSecOps pipeline checks, infrastructure-as-code scanning, staging environment tests.
- *Example:* Moving applications from on-premises to a cloud environment.
- *Impact:* Misconfigured cloud storage could expose sensitive data publicly.

**Access Control Changes**

- *Examples:* Adjusting user privileges, roles, or access to sensitive data.
- *How to handle:* Approval required from both IT Security and data owners; apply least privilege.
- *Example:* Granting database admin rights to a developer.
- *Impact:* Could lead to data exfiltration or privilege misuse.

#### Types of Changes (ITIL / NIST Standards)

**Standard Change**
Low-risk, pre-approved, repeatable, and well-documented. Typically automated or controlled through strict procedures.
- *Example:* Deploying a monthly security patch that has been previously tested.
- *Security impact:* Minimal, as risk is already assessed.

**Normal Change**
Requires risk assessment, approval from the Change Advisory Board (CAB), and a scheduled rollout. Covers most application and infrastructure changes.
- *Example:* Rolling out a new version of a web application.
- *Security impact:* Medium to high; needs structured review, especially for code or access changes.

**Emergency Change**
Performed in response to an urgent need, usually fixing a vulnerability, outage, or security breach. Requires fast-track approval but must be followed by a post-implementation review.
- *Example:* Applying an emergency patch for a zero-day exploit.
- *Security impact:* Very high if not managed; may resolve the threat but introduce instability or misconfiguration.

#### Importance of Monitoring Unapproved Changes

Unapproved changes are a critical operational security risk. Examples include:

- Developer bypassing the DevSecOps pipeline and pushing code directly to production
- Admin modifying firewall rules without CAB approval
- Installing unapproved software on application servers
- Attacker-driven changes, such as:
  - Modifying configuration files or registry keys to maintain persistence
  - Adding unauthorized user accounts or privileged roles
  - Deploying malicious code or scripts disguised as "normal updates"

**Detection methods:**

- **File Integrity Monitoring (FIM):** A security control that monitors critical system and application files for unauthorized or unexpected modifications.
- **SIEM alerts for configuration drift:** SIEM (Security Information and Event Management) aggregates logs from across the enterprise and applies rules to detect abnormal activity, identifying deviations from the approved/expected configuration state. Rules can be custom-defined to match a security baseline (e.g., CIS Benchmarks, hardening policies).
- **Regular audits** comparing system state versus approved change records.
- **Endpoint Detection & Response (EDR):** Focused on detecting suspicious behavior, persistence mechanisms, and attacker tactics.

### 2. Incident Management

#### Definition

Incident Management is the structured process of preparing for, detecting, responding to, and recovering from security incidents that threaten the confidentiality, integrity, or availability of systems and data.

No organization can achieve zero incidents. Threat actors constantly evolve, and even the best-prepared defenses will face breaches, misconfigurations, or insider issues. What differentiates resilient organizations is not avoiding all incidents, but responding quickly and effectively to minimize damage.

#### The Incident Lifecycle

**Detection**
Based on monitoring tools, alerts, and rules mapped to the MITRE ATT&CK matrix (e.g., detecting credential dumping, lateral movement, persistence techniques).
- *Example:* SIEM rule detects unusual authentication attempts.

**Triage**
Assess severity, scope, and business impact.
- *Example:* Confirm if unusual activity is a false positive or real ransomware spreading.

**Containment**
Stop the spread by isolating affected systems, accounts, or networks.
- *Example:* Disable a compromised user account, segment infected servers, block malicious IP addresses.

**Eradication**
Remove the root cause of the attack.
- *Example:* Delete malware, remove persistence mechanisms, patch exploited vulnerabilities.

**Recovery**
Restore normal operations while ensuring the environment is secure.
- *Example:* Restore clean backups, re-enable services, strengthen firewall rules.

**Post-Mortem (Lessons Learned)**
Analyze what happened, why controls failed, and how to improve.
- *Example:* Document the incident timeline, adjust SIEM detection rules, update playbooks.

#### End-to-End Incident Response Example: Ransomware on a File Server

| Phase | Action |
|---|---|
| **Detection** | SOC receives SIEM alert for mass file renaming (attacker encrypting files) |
| **Triage** | Confirm it is active ransomware |
| **Containment** | Disconnect infected servers from the network |
| **Eradication** | Remove malicious binaries, disable compromised accounts |
| **Recovery** | Restore data from clean backups, verify integrity |
| **Post-Mortem** | Update detection rules, train employees on phishing awareness |

#### Incident Playbooks

An incident playbook is a documented, step-by-step guide that defines how an organization should respond to a specific type of security incident.

**Example Playbook: SQL Injection**

| Phase | Action |
|---|---|
| **Detection** | WAF alert on suspicious query patterns (e.g., `' OR 1=1 --`) |
| **Containment** | Block offending IPs, temporarily disable vulnerable app functions |
| **Eradication** | Patch input validation, sanitize queries |
| **Recovery** | Restore affected database, validate data integrity |
| **Lessons Learned** | Add stricter WAF rules, improve developer secure coding training |

### 3. Security Monitoring and SOC Operations

#### What is the SOC?

The SOC (Security Operations Center) is the core of operational security — the team and technical capability that continuously monitors, detects, investigates, and responds to security events across the enterprise. It turns telemetry into timely action and intelligence.

**Core responsibilities:**

- **Log collection & normalization:** Gather and centralize logs from network, endpoints, identity, cloud, and applications.
- **SIEM use cases & correlation:** Transform raw logs into actionable alerts.
- **Alert triage & initial investigation** (Tier 1 SOC).
- **Incident response and remediation** (Tier 2 & 3 and Incident Response team).
- **Threat hunting & proactive detection.**
- **Escalation & coordination** with IT, Forensics, Legal, and Communications.
- **Continuous improvement:** Fine-tune detections, reduce false positives, update playbooks.

#### Key SOC KPIs and Targets

| KPI | Description |
|---|---|
| **MTTD** (Mean Time To Detect) | Average time from intrusion to detection |
| **MTTR / MTR** (Mean Time To Respond / Recover) | Average time from detection to containment/remediation |

### 4. Vulnerability Management

#### Definition

A continuous process of identifying, assessing, prioritizing, remediating, and tracking security weaknesses in systems, applications, and infrastructure. Most breaches exploit known vulnerabilities that were left unpatched. Timely vulnerability management reduces the attack surface dramatically.

#### Lifecycle and Core Components

**1. Identification**
Performed using scanners (e.g., Nessus, Qualys, OpenVAS) and manual reviews. Includes OS patches, application libraries, firmware, misconfigurations, and weak policies. Should be integrated with asset inventory to ensure complete coverage.

**2. Assessment**
Each vulnerability must be scored using a framework:
- **CVSS** (Common Vulnerability Scoring System) → severity score (0–10)
- **KEV** (Known Exploited Vulnerabilities catalog) → indicates if the flaw is actively exploited in the wild
- **EPSS** (Exploit Prediction Scoring System) → probability of exploitation

And contextualized based on: asset criticality, exposure (internal vs. internet-facing), data sensitivity, and business impact.

**3. Prioritization**
Not every vulnerability can be patched at once — a risk-based approach is needed.

Example priority logic:
- Internet-facing + CVSS ≥ 8.0 + listed in KEV → **patch immediately**
- Internal server + CVSS ≥ 7.0 but not actively exploited → **patch within SLA**

**4. Remediation**
- **Patching:** Vendor updates, OS patches, third-party library updates
- **Configuration hardening:** Disabling insecure protocols, enforcing TLS, removing default accounts
- **Compensating controls:** Firewall rules, IPS signatures, EDR rules — used when patching is not immediately possible

**5. Automation**
- Automatic patch tools: WSUS, SCCM, Intune, Ansible, Puppet, Chef
- CI/CD integration: Scanning dependencies before deployment using SCA tools like Snyk or Dependabot

**6. Validation & Reporting**
- Rescan systems post-patching to confirm remediation
- Document metrics: number of critical vulnerabilities remediated, SLA compliance rate, average remediation time
- Feed results back into the risk register and governance board
