
# Secure Software Development Lifecycle (S-SDLC)

---

## Part 1: Theory

### What is Software?

Software is a set of instructions that run on top of hardware. Software and hardware are coupled — the speed at which the set of instructions execute depends on the processor that is part of the hardware.

Generally speaking, there are two types of software:

- **Systems software** — provides a platform for other software to run on and interfaces with the hardware (e.g. operating systems).
- **Application software** — provides functionality that can be executed by end users (e.g. word processors, games, web applications).

There are other types of software such as web servers, database applications, firewalls, and proxies, which can be grouped in either category depending on who is using the application. For an end user, a web server is systems software as it runs the web application they use. However, from an administrator's perspective, it is application software as the administrator configures it to work with the systems software.

---

### Software Development Lifecycle

Irrespective of the type of software, software development follows a lifecycle. Software is developed to meet a set of business requirements. Solutions are created as an interface between the requirements and technical requirements. Technical architecture and software design is derived, which is then channelled into an application using a programming language. The resulting application is tested at various levels and eventually signed off by business users who commissioned the software.

Various methods are used for the software development lifecycle, including but not limited to:

- Waterfall method
- V-model
- Agile methodology
- Extreme Programming (XP)

### Secure Software Development Lifecycle (S-SDLC)

#### What is Software Development Security and Why Do We Need It?

Applications are developed for business purposes. However, if developed without security in mind, they can have vulnerabilities such as SQL injections, XSS, and CSRF.

To ensure security is built into applications, the following practices should be followed:

#### Threat Modelling

The application should be threat modelled to understand what can go wrong from a security perspective. Threat modelling is performed using various methods including STRIDE, DREAD, PASTA, and TRIKE. It can also be performed on paper by noting down the items that can go wrong; however, in the absence of a structured method, the activity may contain blind spots.

**Example 1:**
Applications accept inputs from users. A developer may accept raw input from the end user, build a SQL query and run it against a database. A threat actor may inject malicious characters in the input and retrieve contents of the database. During a threat modelling session, the "what can go wrong" activity can identify malicious injected inputs from the user. The mitigation for this threat would be parametrisation of queries.

**Example 2:**
An application owner decides to accept images located on a server belonging to a third-party domain. During the threat modelling session, security personnel point out that allowing access to cross-origin resources (CORS) may result in malicious and tampered images being rendered on the browser. The developer points out that access to CORS can be restricted by allow-listing the identified domain on the content security policy and on `X-FRAME-OPTIONS`.

#### Secure Coding Guidelines

A library of secure coding guidelines provides guidance to developers in developing applications securely. For example:

- **To address cross-site scripting (XSS):**
  - Add content security policy
  - Ensure input data is sanitised
- **To address clickjacking:**
  - Add content security policy, or set the HTTP header `X-FRAME-OPTIONS` to `SAMEORIGIN` or `DENY`
- **To ensure malicious activities are detected:**
  - Add logging while developing the application

Having this level of detail may not address all vulnerabilities, but will provide a starting point which can be built upon further.

#### Static Code Analysis / Static Application Security Testing (SAST)

Code can have vulnerabilities. To ensure that vulnerabilities are not shipped to production, code needs to be reviewed. Code review can be performed manually or using automated tools. Both have advantages and disadvantages, but applications with large code bases tend to use automated scanning as it is time- and cost-effective and supports the current world of "speed-to-market".

SAST tools can identify vulnerabilities including but not limited to:
- Embedded passwords / secrets
- SQL injection
- Lack of input data validation

Examples of SAST tools include Checkmarx, SonarQube, and Veracode.

#### Dynamic Application Security Testing (DAST)

Running applications have vulnerabilities which need to be tested over and above static code analysis. Again, this activity can be performed manually or using automated tools. Organisations prefer automated testing.

DAST tools identify vulnerabilities including but not limited to:
- Cipher suites on certificates
- Exposed information about web servers
- Injection-based attacks
- Missing content security policy

#### Penetration Testing

Pen testing is usually performed towards the end of the lifecycle and before go-live. It is a combination of controlled testing of identified vulnerabilities and highlighting the risks of open vulnerabilities. Pen testing provides third-party testing that is usually required for compliance standards such as ISO 27001 and PCI-DSS.

#### Findings and Their Resolution

SAST scans, DAST scans, and pen testing result in findings. These findings have a risk rating depending on:
- The ease of discovering the findings
- The difficulty in exploiting them
- Their scores in public vulnerability disclosure databases (CVE, CWE, CVSS)

The findings are reviewed from the perspective of the organisation and the available security controls, based on which the risk scores are adjusted.

> **Example:** A pen tester may report a vulnerability in a software library that processes tax calculations and rate it as critical. Upon review, if it is found that the library is used in an internal application accessed with authentication and MFA, the risk rating may be reduced as appropriate.

Risk ratings are important as they determine the timelines within which findings need to be fixed. These ratings, revised ratings, and timelines depend on the organisation's risk assessment process.

### DevOps

To address the current world of "speed-to-market", organisations use **Continuous Integration and/or Continuous Deployment (CI/CD)**, carried out by the DevOps team using **Infrastructure-as-Code (IaC)**.

CI/CD is carried out using pipelines — files that contain all the activities needed for a deployment, including creation of infrastructure components like virtual machines and database servers.

It is important to:
- Include security in the pipelines to ensure that insecure ports (e.g. port 21) are not exposed to the internet
- Ensure security controls are included for all components
- Secure orchestration tools like Docker Compose and Kubernetes to prevent insecure configurations from impacting the running application

---

### Environments

Applications are deployed in environments dedicated to specific purposes:

- **Development environment** — used by developers to build applications
- **Test environment** — used for testing applications
- **Production environment** — runs the application for end users

Development and test environments are typically referred to as **lower environments** or **non-production environments**.

> **Note:** Software like operating systems also has production environments — they are maintained and managed by the suppliers.

---

### Open Source Software

Open source software is commonly used. Unlike proprietary software, it offers many advantages and comes at little to no financial cost. However, it must be reviewed from a security perspective to ensure that its usage does not impact the application.

Popular open source software includes Unix/Linux, OSSEC, OpenAPI specs, and Apache Tomcat.

A key attribute to consider is the **licence** attached to the software, which may add constraints and permissions for various uses.

---

### Outsourcing

Outsourcing of software development is widely practised. It becomes problematic when S-SDLC is not addressed in the contract, as the organisation may assume it is being carried out by the supplier when it is not.

In such scenarios, organisations should have security personnel who:
- Add security requirements as part of contracts
- Review the met requirements on a periodic basis as agreed

---

### Shadow IT

Shadow IT has evolved from informal, undocumented applications created by teams for specific purposes, into applications commissioned by non-engineering teams such as marketing, sales, or IT.

**Historical shadow IT issues:**
- Applications not documented, maintained by only one or two people
- If those people left, the application became unsupported
- Applications often not built with security in mind

**Modern shadow IT:**
Applications procured or commissioned by non-engineering teams may similarly not have been built with security in mind.

## Part 2: Practice

### When You Join the Organisation

#### Week 1
Settle in.

#### Week 2

**Meet with the Engineering team.**

Ask the head of engineering:
- Is software development in-house or outsourced?
- If in-house, document the roles in the team (typically: development manager, lead developer, Scrum master)
- Is there a security role embedded in the team or from the information security team?
- If outsourced, document supplier roles and the protocol for engaging them
- Speak with the supplier manager about contracts and whether security controls are embedded

**Talk to the Information Security team.**

Understand the processes they have for secure software development and check if any security member is embedded in the engineering team.

**Make a list of stakeholders** across departments such as IT, product development, architecture, marketing, sales, and operations management. This will be useful when checking for applications procured or commissioned without the information security or engineering team's knowledge.

#### Weeks 3–5

Ask the head of engineering about threat modelling and secure coding guidelines. The level of maturity will vary from very little to a fairly mature process.

Ask the following questions:
- How do they include security in the code?
- Are they aware of the various vulnerabilities that applications have?
- Have they heard of the OWASP Top 10 risks?
- Do they conduct any threat modelling?
- Do they have any secure coding guidelines?
- Do they have any tools for SAST and/or DAST?
- Do they have a vulnerability management programme to address findings from those tools?
- Is any training conducted for developers on secure coding? If development is outsourced, do suppliers train their developers in secure coding?

#### Week "X"

Check for shadow IT by speaking to various department heads. Check for software or applications commissioned by marketing teams, product teams — especially those outsourced to a third party — and review the security controls implemented.

#### Week 6

Once gaps in the S-SDLC have been identified, document all of them, assign an owner, and track them. A sample findings document may look like this:

| Finding # | Description | Owner | Impacted Asset(s) | Priority | Budget Approved? | Agreed Road Map | Agreed Date to Close |
|---|---|---|---|---|---|---|---|
| 1 | Missing threat modelling process | Supplier management team | Products developed with outsourced team in XYZ country | High | No | Implement threat modelling requirement in supplier contracts | — |
| 2 | Applications commissioned by marketing teams | InfoSec team | Application that accepts credit card details | High | Yes | Implement S-SDLC for the applications | — |

> **Note:** This activity is time-consuming. It is important to be able to explain security requirements in plain English to non-technical teams. Without owner buy-in, it may be challenging to get any activities completed.

---

### Ongoing Activities

- Work on levelling up inconsistent S-SDLC practices across the organisation
- Consolidate tools where possible (e.g. a single pane of glass view for SAST/DAST)
- Store all threat models in a common folder or single tool
- Maintain a library of secure coding guidelines per language and common libraries
