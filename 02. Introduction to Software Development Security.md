Introduction to Software Development Security
Part 1: Theory:
What is software?
Software is a set of instructions that run on top of hardware. Software and hardware are coupled, if not tightly as the speed at which the set of instructions depend on the processor that is part of the hardware. 
Generally speaking there are two types of software - systems software and applications software.
Systems software provides a platform for other software to run on and interfaces with the hardware. (operating systems)
Application software provide functionality that can be executed by end users (word processors, games, web applications)
There are other types of software like web server, database applications, firewalls, proxies, etc. which can be grouped in either of the categories depending on who is using the application. For an end user, a web server is a systems software as it runs the web application that the end user uses. However from an administrator’s perspective, it is an application software as the administrator is the end user who configures it to work with the systems software.

Software development lifecycle:
Irrespective of the type of software, software development follows a lifecycle. Software is developed to meet a set of business requirements. Solutions are created as an interface between the requirements and technical requirements. Technical architecture and software design is derived which is then channeled into application with programming language. The resulting application is tested at various levels and eventually signed off by business users who commissioned the software.
Various methods are used for software development lifecycle which include, but are not limited to:
Waterfall method
V-model
Agile methodology
Xtreme Programming
etc.

Secure-Software Development Lifecycle
What is software development security and why do we need it:
Applications are developed for business purposes. However, if developed without security in mind, they can have vulnerabilities in them. For example SQL injections, XSS, CSRF, etc.
To ensure security is built into application:
Threat Modelling: The application should be threat modelled to understand what can go wrong from a security perspective.
Threat modelling is performed using various methods including STRIDE, DREAD, PASTA, TRIKE. 
Threat modelling can be performed on paper as well  by noting down the items that can go wrong. However, in the absence of a method, the activity may contain blind spots.
	For example:
		Example 1:
 Applications accept inputs from users. A developer may accept raw input from the end user, build a SQL query and run it against a database. A threat actor may inject malicious characters in the input and retrieve contents of the database. 
During a threat modelling session, “what can go wrong” activity can identify malicious injected inputs from the user. 
The mitigation for this threat would be parametrisation of queries.
		Example 2:
An application owner decides to accept images located on a server belonging to a third party domain.
During the threat modeling session, security personnel point out that allowing access to cross-origin resources (CORS) may result in malicious and tampered images being rendered on the browser.
The developer points out that access to CORS can be restricted by allow-listing the identified domain on content security policy and on X-FRAME-OPTIONS.
Secure Coding Guidelines: A library of secure coding guidelines provides guidance to developers in developing applications securely.
For example:
To address cross-site-scripting vulnerability:
It is important to add content security policy 
Ensure input data is sanitised
To address click jacking
It is important to add content security policy OR set HTTP header X-FRAME-OPTIONS to SAMEORIGIN or DENY.
To ensure that any malicious activities are detected, logging should be added while developing the application.
Having this level of details may not address all the vulnerabilities but will provide a starting point which can be built further upon  	

Static code analysis / Static Application Security Testing (SAST)
Code can have vulnerabilities. To ensure that vulnerabilities are not shipped to the production environment, code needs to be reviewed.
Code review can be performed manually or using automated tools.
Both have their own advantages and disadvantages, but applications with large code bases tend to use automated scanning as it is time and cost effective. And supports the current world of “speed-to-market”.
SAST tools can identify vulnerabilities including but not limited to embedded passwords / secrets, SQL injection, lack of input data validation
Examples of SAST include Chekmarx, SonarCube, Veracode.

Dynamic Application Security Testing (DAST)
Running applications have vulnerabilities which need to be tested over and above static code analysis.
Again this activity can be performed manually or using automated tools.
Organisations prefer using automated testing.
DAST tools look for and identify vulnerabilities including but not limited to, cipher suites on certificates, exposed information about web servers, injection based attacks, missing content security policy.

Pen Testing 
Pen testing is usually performed towards the end of the lifecycle and before go-live.
Pen testing is a combination of controlled testing of identified vulnerabilities and highlighting the risks of open vulnerabilities
Pen testing provides third party testing that is usually required for compliance standards like ISO27001 and PCI-DSS.

Findings and their resolution:
SAST scans, DAST scans and pen testing result in findings. These findings have a risk rating depending on the ease of discovering the findings, difficulty in compromising the findings, and the scores of the findings in public vulnerability disclosure databases like CVE, CWE, and CVSS scores.
The findings are reviewed from the perspective of the organisation and the available security controls, based on which the risk scores are adjusted.
For example, a pen tester may report on a finding about a vulnerability identified in a software library that processes tax calculations and report it as critical. Upon review, if it is found that the software library is used in an internal application which is accessed with authentication and MFA, the risk rating may be reduced as appropriate.
Risk ratings on findings are very important as they determine the timelines before which they need to be fixed. These risk ratings, the revised risk rating and the timelines to fix them depends on the risk assessment process in the organisation.
	
DevOps:
To address the current world of “speed-to-market”, organisations use Continuous Integration and/or Continuous Deployment (shortened to CI/CD) which is carried out by the devops team using Infrastructure-as-Code (IAC). 
CI/CD is carried out using pipelines which are files that contain all the activities that need to be carried out for a deployment. These activities include creation of infrastructure components like virtual machines, database servers, etc.
It is important to include security in the pipelines to ensure that insecure ports like port 21 are not opened to the internet, security controls are included for the components, etc. 
It is important to secure the orchestration tools like Docker Compose and Kubernetes to ensure that any insecure configurations do not impact the running application.

Environments:
Applications are deployed in environments dedicated to purposes. For example, a development environment is meant to be used by developers to develop applications. Test environments are meant for testing the applications and production environments run the applications for the users who it is meant for. Typically development and test environments are referred to as lower environments or non-production environments.
It can be argued that software / applications like operating systems do not have a production environment. Well, they do. Except that these environments are maintained and managed by the suppliers.

Open source software:
Open source software is commonly used. Unlike proprietary software, open source software offers many advantages and comes at little to no financial costs. However, they need to be reviewed from a security perspective to ensure that usage of such software does not impact the application. Popular open source software include Unix / Linux, OSSEC, OpenAPI specs, Apache Tomcat, etc.
The key attribute of open source software that needs to be considered is the license that is attached to it and which may add constraints and permissions for various uses of the software.

Outsourcing:
Outsourcing of software / application development is practiced. Outsourcing is an activity where the development activity is carried out by a supplier with whom the organisation has a contract to develop applications. It becomes tricky when secure-SDLC is not addressed in the contract as the organisation may assume that S-SDLC is carried out by the supplier and the supplier may not do it.
In such a scenario organisations have security personnel who look into adding security requirements as a part of contract and review the met requirements on a periodic basis as agreed.

Shadow IT:
Shadow IT is not such a huge thing now but it has metamorphosed into applications being commissioned by non-engineering teams like the marketing team or sales team or IT team.
In the past shadow IT was a set of applications that would be created by teams to ease work or for a very specific purpose. They would not normally be documented and would be maintained by one or two people. The issue with such applications is that in the event the people or team that created the application left the organisation. Due to lack of knowledge or memory, the applications would be unsupported and would cease to support the functionality. Also these applications would not necessarily have been built with security in mind. The new avatar of shadow IT are applications that are procured or commissioned by non-engineering teams, which again may not necessarily have been built with security in mind.
	


Part 2: Practice:
When you join the organisation:
Week 1:
Settle in

Week 2:
Meet with the Engineering team. 
Ask the head of the engineering department about who works on software development - in-house team or is the software development outsourced.
If software development is carried out in-house, document the roles that are a part of the team. Typically there would be a development manager, a lead developer and a Scrum master from the project management / program management team.
Ask if there is any security role embedded in the team or from the information security team.
If software development is carried out by an outsourcing supplier, document the roles that work in the supplier’s organisation. The roles may still be the same as in-house teams, but it is possible there would be a protocol to talk to the people in those roles.
Another good source of information is the supplier manager, who generally would know about contracts and if security controls are embedded in contracts.
However, wherever the development is, the questions would remain the same.

Week 2:
Talk to the Information security team and understand the process(es) they have for secure software development. Check with the team if any security member is embedded in the engineering team.

Make a list of the stakeholders in the organisation in departments like IT, product development, architecture, marketing, sales, operations management (please note that these departments may be named differently in the organisations you work in):
This list will come handy later on when checking on applications procured or commissioned without information security team’s or engineering team’s knowledge.

Week 3, week 4 and week 5:
Ask the head of the engineering department about threat modelling and secure coding guidelines. In real life the level of maturity of threat modelling and security coding may vary from very little to a fairly mature process. 
Ask the following questions:
How do they include security in the code?
Are they aware of the various vulnerabilities that applications have?
Have they heard of OWASP Top 10 risks?
Do they conduct any threat modelling?
Do they have any secure coding guidelines?
Do they have any tools for SAST and/or DAST
Do they have a vulnerability management program to address the findings from the tools?
Is any training conducted for the developers for secure coding? If the development is outsourced, do the suppliers train their developers in secure coding?


Week “x”:

Check for software / applications commissioned by marketing teams, product teams especially the ones outsourced to a third party. If product teams, marketing teams commission applications, check for the security controls implemented.

Ongoing activities:
It is very likely that you will find inconsistencies for the way S-SDLC is used across the organisation.
As an ongoing activity work on levelling it up.
Consolidate as many tools as possible. For example a single pane of glass view for SAST tools, DAST
Storing all threat models in a common folder or in one single tool, is used.
Maintaining a library of secure coding guidelines per language and common libraries.
